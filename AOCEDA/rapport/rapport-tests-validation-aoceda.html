03Logique du code par domaine

Les six sections suivantes détaillent, pour chaque application testée, le mécanisme concret qui garantit un comportement correct — pas seulement « le test passe », mais pourquoi le code se comporte correctement dans les cas limites (perte réseau, rebond de mesure, changement de mot de passe pendant une session active, arrondi monétaire, etc.).

Authentification JWT & révocation immédiate

apps/accounts

L'API est stateless (JSON Web Tokens, SimpleJWT) : un jeton d'accès reste valide 30 minutes une fois émis. Problème à couvrir : si un client change son mot de passe (compte compromis, appareil volé), un jeton déjà émis ne doit plus fonctionner — même s'il n'est pas encore expiré.

Principe
Chaque jeton porte un claim iat (date d'émission). Le compte porte un champ password_changed_at. Un jeton est rejeté si son iat est antérieur au dernier changement de mot de passe — quel que soit son état d'expiration.
Implémentation
class TokenAuthentication(JWTAuthentication):
    def get_user(self, validated_token):
        user = super().get_user(validated_token)
        changed_at = getattr(user, 'password_changed_at', None)
        if changed_at is not None:
            iat = validated_token.get('iat')
            if iat is not None and iat < int(changed_at.timestamp()):
                raise AuthenticationFailed(
                    "Ce jeton a été émis avant votre dernier changement "
                    "de mot de passe. Reconnectez-vous.",
                    code='token_before_password_change',
                )
        return user
Cas limite traité
iat est précis à la seconde, password_changed_at à la microseconde : comparer aux secondes entières (int(...)) évite de rejeter à tort un jeton fraîchement émis dans la même seconde que le changement de mot de passe.
Testé par
apps/accounts/tests.py — suite accounts (31 tests).

Ingestion des mesures & anti-rebond ON/OFF

apps/sensors

L'ESP32 poste une mesure par capteur toutes les ~2 secondes. Une chute de courant très brève (variation naturelle de charge) ne doit pas faire clignoter l'état d'un appareil entre ON et OFF à chaque cycle — le dashboard afficherait un historique illisible et déclencherait de fausses alertes.

Principe
Passage à ON immédiat dès la première mesure active (réactivité), mais passage à OFF seulement après CONFIRM_OFF = 3 échantillons consécutifs sans courant (stabilité) — dissymétrie volontaire, cohérente avec le comportement réel d'un appareil électrique.
Implémentation
CONFIRM_OFF = 3
...
echantillon_on = (etat_recu == 'ON' and puissance > 0)
capteur.derniereLecture = now

if echantillon_on:
    capteur.cptOffConsecutifs = 0
    capteur.etatCourant = 'ON'
else:
    capteur.cptOffConsecutifs = min(capteur.cptOffConsecutifs + 1, CONFIRM_OFF)
    if capteur.cptOffConsecutifs >= CONFIRM_OFF:
        capteur.etatCourant = 'OFF'
Cas limite traité
Le tampon hors-ligne de l'ESP32 (mesures rejouées après une coupure réseau) garde l'horodatage réel de mesure (timestamp) tout en mettant à jour derniereLecture à l'heure de réception — un appareil qui vient de se reconnecter et rejoue son tampon n'apparaît donc jamais « hors ligne » à tort.
Testé par
apps/sensors/tests.py — suite sensors (22 tests).

Moteur de règles d'alerte & anti-spam

apps/alerts

Un dépassement de seuil soutenu doit générer une alerte — mais une seule, pas une par mesure reçue. Sans garde-fou, un ESP32 postant toutes les 2 secondes produirait jusqu'à ~1 800 alertes (et autant d'e-mails) par heure de dépassement continu.

Principe
Déduplication par cooldown : avant de créer une alerte, on vérifie qu'aucune alerte du même type n'existe déjà pour ce capteur dans une fenêtre récente (15 min pour un dépassement de seuil, 60 min pour une consommation nocturne).
Implémentation
def _alerte_recente(client, capteur_id, type_alerte, minutes):
    depuis = timezone.now() - timedelta(minutes=minutes)
    return Alerte.objects.filter(
        client=client, type=type_alerte,
        mesure__capteur_id=capteur_id, createdAt__gte=depuis,
    ).exists()

def _evaluer_mesure(client, rule, mesure):
    if mesure.puissance > rule.puissanceMax_W:
        if not _alerte_recente(client, mesure.capteur_id, 'DEPASSEMENT_SEUIL', 15):
            alert = Alerte.objects.create(client=client, mesure=mesure,
                type='DEPASSEMENT_SEUIL', message=msg, sévérité='Critique')
            send_alert_email(alert)
Cas limite traité
La fenêtre de surveillance nocturne accepte une plage à cheval sur minuit (ex. 22h→05h) : heureDébutNuit <= heureFinNuit détermine si on teste un intervalle simple ou un OR sur les deux bornes. Le mode absence suspend uniquement l'alerte nocturne, jamais le dépassement de seuil ni le crédit bas — une absence rend au contraire ces deux-là plus utiles.
Testé par
apps/alerts/tests.py — suite alerts (12 tests).

Facturation CIE — grille tarifaire progressive

apps/analytics

La grille CIE domestique basse tension applique deux tranches de prix dont le seuil dépend de la puissance souscrite (ampérage), et bascule automatiquement certains profils vers le tarif Social. Une erreur d'arrondi sur une opération monétaire n'est pas acceptable.

Principe
Tarification à deux tranches (seuil_t1 dépendant de l'ampérage), tout calcul en Decimal (jamais en float) avec arrondi ROUND_HALF_UP explicite à chaque étape intermédiaire, pour éviter toute dérive d'arrondi binaire sur des montants FCFA.
Implémentation
def calculer_facture_mensuelle(kwh, amperage=10, type_tarif="general"):
    kwh_t1 = min(kwh, p["seuil_t1"])
    kwh_t2 = max(Decimal("0"), kwh - p["seuil_t1"])
    montant_t1 = _round(kwh_t1 * p["prix_t1"])
    montant_t2 = _round(kwh_t2 * p["prix_t2"])
    taxes = _round(kwh * p["taxes_par_kwh"] + p["taxe_fixe"])
    total = _round(montant_t1 + montant_t2 + p["prime_fixe"] + taxes)
Cas limite traité
Le tarif Social n'existe qu'en 5A ; le 5A « général » n'existe pas à la CIE. parametres_tarif() route donc systématiquement tout compte 5A vers la grille Social, quel que soit le type_tarif demandé — impossible de facturer un 5A au tarif général par erreur.
Testé par
apps/analytics/tests.py — suite analytics (32 tests).

Assistant IA — function calling borné au client

apps/ai_assistant

L'assistant conversationnel peut interroger les données réelles du client (consommation, factures, alertes) via des outils exposés au LLM. Deux risques à couvrir : que le LLM boucle indéfiniment sur des appels d'outils, et qu'il puisse accéder aux données d'un autre client.

Principe
Boucle « function calling » bornée à MAX_ITERATIONS_OUTILS tours ; le dernier tour force une réponse texte plutôt qu'un nouvel appel d'outil. Chaque outil est exécuté côté serveur via executer_outil(client, ...) — le client authentifié est injecté par le serveur, jamais fourni par le LLM : structurellement impossible de lire les données d'un autre compte.
Implémentation
for iteration in range(MAX_ITERATIONS_OUTILS):
    dernier_tour = (iteration == MAX_ITERATIONS_OUTILS - 1)
    texte, tool_calls, t_in, t_out = adaptateur.appeler(
        system_instruction, messages, OUTILS_SPEC, dernier_tour)
    if tool_calls and not dernier_tour:
        for tc in tool_calls[:MAX_APPELS_OUTILS_PAR_TOUR]:
            resultat = executer_outil(client, tc['name'], tc['arguments'])
            messages.append({"role": "tool", "tool_call_id": tc['id'],
                              "name": tc['name'], "content": json.dumps(resultat, default=str)})
        continue
    return texte, outils_utilises, tokens_in, tokens_out
Cas limite traité
Si la clé API du fournisseur LLM est absente ou invalide, l'adaptateur renvoie None et le code bascule sur repli silencieux (provider = 'standard'/assistant local) au lieu de faire échouer la conversation.
Testé par
apps/ai_assistant/tests.py — suite ai_assistant (6 tests).

Agrégations tableau de bord

apps/dashboard & analytics

Le tableau de bord agrège potentiellement des centaines de milliers de mesures (voir test de charge, §10). Sommer et grouper ces mesures en Python ferait exploser le temps de réponse et la mémoire du serveur.

Principe
Toute agrégation (somme d'énergie par jour/mois, comptage par type) est déléguée à PostgreSQL via l'ORM Django (Sum, Count, TruncDate/TruncMonth), jamais recalculée ligne par ligne côté application.
Implémentation
MesureEnergie.objects.filter(capteur__client=client, timestamp__gte=start)
    .annotate(jour=TruncDate('timestamp'))
    .values('jour').annotate(total_kwh=Sum('energie'))
    .order_by('jour')
Cas limite traité
Combiné aux index PostgreSQL sur sensor_id et timestamp (§10), cette agrégation en base — plutôt qu'en Python — est ce qui permet le temps de réponse de ≈0,4 s mesuré sur 1 000 000 de lignes.
Testé par
apps/dashboard/tests.py (3 tests) et apps/analytics/tests.py (32 tests).

09Test d'intégration — flux complet de bout en bout

Le scénario valide la chaîne complète depuis l'acquisition physique jusqu'à l'affichage sur le tableau de bord : un chargeur d'ordinateur portable (65 W) est branché sur la prise surveillée par le capteur n°2, puis la mesure est vérifiée traitée et disponible côté serveur (API et base de données) dans un délai inférieur à 5 secondes (KPI 2).

Délai cible (KPI 2)< 5 s
Délai moyen obtenu3,2 s (50 essais consécutifs)

Précision méthodologique. La latence de 87 ms (tests unitaires du dispositif IoT, §5.4.1 du mémoire) mesure uniquement le transport réseau d'une trame HTTP brute ESP32 → API. Les 3,2 s du KPI 2 couvrent la chaîne complète : réception, traitement backend et écriture en base PostgreSQL.
